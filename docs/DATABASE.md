# Database Setup Guide for Scout

## Overview

Scout uses **Supabase** (PostgreSQL) as the backend database. This guide walks
you through setting up all 10 tables and explains the relationships between
them.

## Architecture Summary

```
┌─────────────────────────────────────────────────────────────────┐
│                    SUPABASE (PostgreSQL)                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  auth.users (Supabase built-in)                                 │
│       ↓                                                         │
│  profiles (extends auth.users)                                  │
│       ├→ user_settings                                          │
│       ├→ pets                                                   │
│       ├→ sitter_invites → sitter_sessions                       │
│       └→ daily_logs ← daily_tasks, sitter_sessions              │
│                                                                 │
│  pets                                                           │
│       ├→ daily_logs                                             │
│       ├→ daily_tasks                                            │
│       ├→ streaks                                                │
│       ├→ inventory                                              │
│       └→ product_recommendations                                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## Tables & Relationships

### 1. **profiles** (extends Supabase auth.users)

Stores user information for both pet owners and sitters.

```
id (UUID, PK) → auth.users.id
├ role: 'owner' | 'sitter'
├ display_name: string
├ email: string
├ avatar_url: string (optional)
└ timestamps
```

**Relations:**

- 1:1 with `user_settings`
- 1:many with `pets` (as owner_id)
- 1:many with `daily_logs` (as logger_id)
- 1:many with `sitter_invites` (as owner_id)
- 1:many with `sitter_sessions` (as sitter_id or owner_id)

---

### 2. **user_settings**

Stores user preferences and notification settings.

```
id (UUID, PK)
├ user_id (UUID, FK → profiles.id) UNIQUE
├ notifications: {
│   dailyReminders: boolean,
│   missedTaskAlerts: boolean,
│   sitterUpdates: boolean,
│   weeklyDigest: boolean
│ }
├ theme: 'light' | 'dark' (optional)
├ language: string (optional)
└ timestamps
```

---

### 3. **pets**

Stores pet information (dogs, cats, etc.).

```
id (UUID, PK)
├ owner_id (UUID, FK → profiles.id)
├ name: string
├ species: string ('dog', 'cat', etc.)
├ breed: string (optional)
├ date_of_birth: DATE (optional)
├ gender: 'male' | 'female' | 'unknown'
├ weight: decimal (lbs)
├ coat_color: string
├ size: 'small' | 'medium' | 'large' | 'extra-large'
├ personality: string
├ medical_notes: string
├ is_spayed_neutered: boolean
├ avatar_url: string (generated by fal.ai)
├ health_context: string (for LLM insights)
└ timestamps
```

**Relations:**

- Many-to-one with `profiles` (owner_id)
- 1:many with `daily_logs`, `daily_tasks`, `streaks`, `inventory`,
  `product_recommendations`, `sitter_invites`, `sitter_sessions`

---

### 4. **daily_logs**

Records every action logged (feeding, walk, medicine, play) with photo evidence.

```
id (UUID, PK)
├ pet_id (UUID, FK → pets.id)
├ logger_id (UUID, FK → profiles.id) — owner or sitter
├ activity_type: 'feeding' | 'walk' | 'medication' | 'play'
├ notes: string
├ photo_url: string
├ logged_at: TIMESTAMP — when activity actually happened
└ timestamps
```

**Used by:**

- `/api/actions` (POST to create, GET to list today's)
- `/api/fulfillment` (calculates hunger, exercise, medicine from these logs)
- `daily_tasks` can create logs via completion

---

### 5. **daily_tasks**

Predefined tasks for each day (recurring routine). Owner creates these
templates.

```
id (UUID, PK)
├ pet_id (UUID, FK → pets.id)
├ owner_id (UUID, FK → profiles.id)
├ category: 'food' | 'exercise' | 'medicine'
├ label: string (e.g., "Morning kibble (1 cup)")
├ time: string (e.g., "7:00 AM") — optional
├ note: string (e.g., "Give with food")
├ is_completed: boolean
├ completed_at: TIMESTAMP (when marked done)
├ date: DATE (YYYY-MM-DD for grouping)
└ timestamps
```

**Used by:**

- `/api/tracker` (GET to fetch daily_tasks for a pet, PATCH to toggle
  completion)
- Linked to `streaks` via category

---

### 6. **streaks**

Tracks consecutive "perfect days" (all tasks completed in a category).

```
id (UUID, PK)
├ pet_id (UUID, FK → pets.id)
├ category: 'food' | 'exercise' | 'medicine' (UNIQUE with pet_id)
├ current_streak: integer (days in a row)
├ last_completed_date: DATE (most recent perfect day)
└ timestamps
```

**Used by:**

- `/api/fulfillment` (returns streaks)
- `/api/tracker` (shows streak badges)

**How it works:**

1. When all `daily_tasks` for a pet+category on a given date are marked complete
2. If yesterday's date had a complete streak too, increment `current_streak`
3. Otherwise, reset to 1
4. Update `last_completed_date` = today

---

### 7. **sitter_invites**

Invites to potential sitters/family members. Uses token-based email links.

```
id (UUID, PK)
├ owner_id (UUID, FK → profiles.id)
├ pet_id (UUID, FK → pets.id) — which pet being cared for
├ email: string — invite recipient
├ role: 'full_access' | 'view_only'
├ token: string UNIQUE (secret link token)
├ permissions_scope: string[] (e.g., ['read:pet', 'write:log'])
├ expires_at: TIMESTAMP
├ accepted_at: TIMESTAMP (when sitter accepted)
├ accepted_by: UUID (FK → profiles.id) — who accepted
└ timestamps
```

**Used by:**

- `/api/sitters/invite` (POST to create invite)
- Link: `domain.com/accept-invite?token=xyz` → creates sitter profile + maps to
  their logs

---

### 8. **sitter_sessions**

Active caregiving sessions (when a sitter is actively looking after the pet).

```
id (UUID, PK)
├ pet_id (UUID, FK → pets.id)
├ sitter_id (UUID, FK → profiles.id)
├ owner_id (UUID, FK → profiles.id)
├ invite_id: UUID (FK → sitter_invites.id) — optional
├ started_at: TIMESTAMP
├ ended_at: TIMESTAMP (optional, NULL if still active)
├ notes: string
└ timestamps
```

**Used by:**

- Dashboard: show active sitter + activity feed
- RLS policy: sitter can only log activities during active session
- `/api/actions` can filter which sitter's activities to show

---

### 9. **inventory**

Stores current stock of food, toys, medicine.

```
id (UUID, PK)
├ pet_id (UUID, FK → pets.id)
├ item_type: 'toy' | 'medicine' | 'food'
├ name: string
├ quantity: decimal
├ unit: string (e.g., 'lbs', 'tablets', 'count')
├ notes: string
├ last_restocked_at: TIMESTAMP
└ timestamps
```

**Future use:** Low stock notifications, auto-reorder reminders.

---

### 10. **product_recommendations**

AI-generated product recommendations (cached from Chewy or similar).

```
id (UUID, PK)
├ pet_id (UUID, FK → pets.id)
├ external_product_id: string (from Chewy API)
├ name: string
├ brand: string
├ image_url: string
├ chewy_url: string
├ price: decimal
├ original_price: decimal (optional)
├ confidence_score: numeric 0-100 (how relevant to pet)
├ reason_snippet: string (why it's recommended)
├ generated_at: TIMESTAMP
├ expires_at: TIMESTAMP (cache expiry — refresh after this)
└ created_at
```

**Used by:**

- `/api/recommendations?petId=...` (fetch or generate if expired)
- Carousel component on dashboard

## Setup Steps

### Step 1: Create Supabase Project

1. Go to [supabase.com](https://supabase.com)
2. Create a new project
3. Copy `Project URL` and `anon key` to your `.env.local`

```env
NEXT_PUBLIC_SUPABASE_URL=https://xxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=xxx
SUPABASE_SERVICE_ROLE_KEY=xxx
```

### Step 2: Run Migration

1. Go to Supabase Dashboard → SQL Editor
2. Create a new query
3. Copy the entire content from
   `supabase/migrations/001_create_scout_schema.sql`
4. Paste and run
5. You should see all 10 tables created ✅

### Step 3: Create Supabase Client

Create `lib/supabase.ts`:

```ts
import { createClient } from '@supabase/supabase-js';

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseAnonKey = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;

export const supabase = createClient(supabaseUrl, supabaseAnonKey);
```

### Step 4: Install Supabase Client

```bash
pnpm add @supabase/supabase-js
```

## Query Examples

### Get all logs for a pet today

```ts
const { data, error } = await supabase
  .from('daily_logs')
  .select('*')
  .eq('pet_id', petId)
  .gte('logged_at', todayStart.toISOString())
  .order('logged_at', { ascending: false });
```

### Get daily tasks for a pet

```ts
const { data, error } = await supabase
  .from('daily_tasks')
  .select('*')
  .eq('pet_id', petId)
  .eq('date', '2026-04-01')
  .order('time');
```

### Mark task complete + update streak

```ts
// 1. Update task
await supabase
  .from('daily_tasks')
  .update({ is_completed: true, completed_at: new Date().toISOString() })
  .eq('id', taskId);

// 2. Check if all tasks in category done today
const completedTasksCount = await supabase
  .from('daily_tasks')
  .select('*')
  .eq('pet_id', petId)
  .eq('category', category)
  .eq('date', today)
  .eq('is_completed', true)
  .count('exact', { head: true });

// 3. If all done, update streak...
```

## Row Level Security (RLS) Policies

All tables have RLS enabled. Key rules:

- **Owners** can CRUD their own pets + tasks + logs
- **Sitters** can only READ/WRITE logs during active sessions
- **Sitters** can only see pets they're invited to
- **Users** can only read their own settings

If you need to bypass RLS for testing, use the `SUPABASE_SERVICE_ROLE_KEY` in a
server-side function.

## Notes

- **timestamps**: Always use ISO 8601 format (`new Date().toISOString()`)
- **timezone-aware**: All timestamps include timezone info via
  `TIMESTAMP WITH TIME ZONE`
- **Indexes**: Added for fast queries on frequently accessed columns
- **FK cascades**: Deleting a pet cascades to all related logs, tasks, etc.
- **UUIDs**: All primary keys use UUID v4 for security + global uniqueness
